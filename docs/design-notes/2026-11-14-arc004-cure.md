# ARC-004 (fuel#680): what the 204 sites are, the cure per group, and what the splits look like after

PM [TASK] fuel-ARC-004-cure-note (2026-11-14). The Fuel lane is the architect for this; the questions are the PM's: per group,
(1) real violation or wrong declaration, (2) cure and its cost, (3) order, (4) what to accept for now. Everything below is
**measured** unless labelled otherwise. Method: coderipper 0.43.54 (local) run as `coderipper check ARC-004 --workspace
--profile extended` on committed `origin/main` (26c619dc4 = 0.47.31): it reads **10,055 public signature sites in policy
components and reports 204**, the same 204 as CI's 0.43.77 job (run 43652961607), so the local binary reproduces CI for this
rule. Two declaration experiments were run in a throwaway worktree (scratch commits, not pushed); they are reported as measured
counts, not as a proposal to edit the declaration to make the tool quiet.

## 0. The rule and the declaration it reads

ARC-004 flags a public signature of a **policy** component that names a type from an **adapter/volatile** component's crate.
`.coderipper.toml` (v0.47.30) declares `loaders` and `backends` as `role = "adapter"`; `dispatch`, `tensor`, `models`, `contract`
(which holds `fuel-formats`) as `role = "policy"`. The declaration was derived from the crate graph, not argued from the code, so
every finding is first a question about the declaration.

| group | sites | files | crates (policy side -> named side) |
| --- | --- | --- | --- |
| G1 `models` -> `loaders`, type `MmapedSafetensors` | 175 | 134 | fuel-transformers 168, fuel-nn 5, fuel-model-llama 1, fuel-model-phi 1 |
| G1b `models` -> `loaders`, `gguf_mmap::MmapedContent` / `gguf_file::Content` | 2 | 2 | fuel-transformers |
| G2 `tensor` -> `loaders`, `MmapedSafetensors` | 3 | 1 | fuel-tensor `lazy.rs` (`load_tensor_as_f32`, `load_transposed_matrix*`) |
| G3 `dispatch` -> `backends` | 18 | 6 | fuel-memory 4, fuel-dispatch 14 |
| G4 `tensor` -> `backends` | 6 | 4 | fuel-tensor |
| total | **204** | | |

(PM's "177 models->loaders" = G1 + G1b; "3 tensor->loaders" = G2. G1 is 175 MmapedSafetensors rows over **134 files**, of which
168 are `load_from_mmapped` in `fuel-transformers/src/models/lazy_*.rs`.)

## 1. G1, G1b, G2: `fuel_loaders` types in model and tensor signatures (180 sites)

**(1) Real or declaration?** Both, and the two halves have different answers.
- `fuel-loaders` is **not an adapter by dependency**: it depends on `fuel-backend-contract`, `fuel-formats`, `fuel-ir`,
  `fuel-quantized` and external format crates (`mlmf-*`, `safetensors`, `memmap2`); it names no backend, `Tensor`, `Storage` or
  `Device` (its own `Cargo.toml` description says so). `fuel-formats`, which does the same kind of work and also holds `memmap2`
  (`MmapedFile`), is declared policy/stable. Declaring one adapter and the other policy is not a distinction the code makes.
- But the *type* is a real coupling: `MmapedSafetensors` is a file-mapping handle, and 168 model constructors take it by
  reference, so a model's public constructor is tied to one file technology rather than to "a source of tensor views".
- **Measured:** setting `loaders` to `role = "policy"` (one line) takes ARC-004 from **204 to 24** (the 24 are G3 + G4, exactly).
  That is the proof that the findings are not about backends. It is **not the cure I recommend**, because it makes the tool
  quiet without removing the coupling, and the declaration edit would be evidence of nothing.

**(2) Cure and cost.** *Cheapest: one move, no breaking change.* Move `MmapedSafetensors` and `BufferedSafetensors`
(`fuel-loaders/src/safetensors.rs`, 342 lines, no `crate::` references: it uses `fuel-ir`, `mlmf-core`, `mlmf-safetensors`,
`safetensors`) into `fuel-formats` next to `MmapedFile`, `pub use` them from `fuel_loaders::safetensors`, and repoint the 135 flagged
files' (134 + `fuel-tensor/src/lazy.rs`) signatures to `fuel_formats::safetensors::...` by a mechanical rewrite. The type's identity does not change (a re-export
is the same type), so **no published API breaks** and no caller changes: 231 files mention the two names today and all keep
compiling. Cost: 1 file moved, 2 dependencies added to `fuel-formats` (`mlmf-core`, `mlmf-safetensors`, both 0.11.29, declared per crate in `fuel-loaders/Cargo.toml`, not workspace deps),
about 135 mechanical edits, one PR, one version bump (patch). The catch: it puts two `mlmf` crates (0.11.x, volatile) under a
component declared `stable`; that is a declaration question for the PM/architect (relabel `fuel-formats` or keep mlmf out of
it), not a code obstacle. G1b and G2 follow the same pattern (`Content`, `MmapedContent` are in the GGUF half of `fuel-loaders`,
which sits on `fuel-formats::gguf`): move them the same way, or leave them accepted (section 4) because they are 2 sites.

*Better, later: a trait boundary.* A `TensorSource` trait in `fuel-formats` (`get(name) -> TensorView`, `names()`), implemented by
the mmap and buffered types, with the constructors taking `&dyn TensorSource` / `&impl TensorSource`. Source-compatible for any
caller passing a `&MmapedSafetensors` (it coerces), but it is 135 signature rewrites plus the methods the 168 bodies call (not
measured: I did not enumerate them), and it lets a model load from GGUF, bytes or a test fixture. That is the seam-1 contract
(ROADMAP row 138), so I would define it there, after the move, rather than do both at once.

**(3) Order.** First (smallest, no break, removes 175-180 of 204 findings).

## 2. G3 `dispatch` -> `backends` (18) and G4 `tensor` -> `backends` (6)

All 24 are signatures that name a concrete backend type; every one is `#[cfg(feature = "cuda"|"vulkan"|"metal")]`-gated or the
unconditional `CpuStorageBytes`. They fall in four kinds with different answers:

| kind | sites | what it is |
| --- | --- | --- |
| K1 closed storage enum `BackendStorage::{Cpu,Cuda,Metal,Vulkan}` (fuel-memory) | 4 | the enum **is** the storage seam |
| K2 device handles held/returned by dispatch: `DeviceRegistry::{with,registered}_{cuda,vulkan}[_by_identity]` (6), `CudaProbeDevice::new` (1), `vulkan_verify_only_on` (1), `CapturedDecode.run` (1) | 9 | dispatch holds live device objects |
| K3 kernel-wrapper helpers `cpu_input`, `cpu_output`, `cuda_input`, `cuda_output`, `qmatmul_cpu_by_type` | 5 | glue shared with the vendor adapter crates |
| K4 `fuel-tensor` device bridges: `as_device` x3 (cuda, metal, vulkan modules), `realize_f32_cuda`, `realize_f32_vulkan`, `realize_many_f32_cuda` | 6 | backend-gated public API of the policy crate |

**K1: not a violation; the declaration is right to be silent only because it is a decision.** The ruling of 2026-11-01 (CireSnave,
via the PM, ROADMAP row 137 S3) is that the **closed `BackendStorage` enum plus `BackendStorageOps` methods is the storage
seam, and trait objects are revisited only if backends ever live outside Fuel**. An enum whose variants hold each backend's
storage necessarily names those types. **Measured, the alternative costs:** the enum is matched at 760 lines in 59 files
across 8 crates; making the payload opaque would break all of them. **Measured, the declaration alternative:** moving
`fuel-memory` into its own adapter component (so the enum is "infrastructure") takes ARC-004 from 24 to **93**, because every
`dispatch` signature that names `Storage` then leaks: the finding moves, it does not leave. So K1 is accepted by the ruling
(section 4); it is not cured.

**K2/K3/K4: real, and they are exactly row 137 step 6.** Row 137's S3 analysis lists "move backend-gated code out of
`fuel-dispatch`" and names `fuel-tensor`'s backend-specific arms in `pipelined_bridge`; these 20 sites are the public surface of
that code. Callers (measured, `git grep` on `origin/main`): `cpu_input` 137 lines / 5 files and `cpu_output` 72 / 3, used mostly
by `fuel-mkl-cpu-backend` and `fuel-aocl-cpu-backend` (vendor adapters that sit **above** dispatch and import its helpers: an
inverted direction in spirit, allowed by the layering only because the helpers are `pub`); `cuda_input` 69 / 6, `cuda_output` 50 / 5
(`fuel-cuda-dispatch`); `with_cuda` 14 lines / 7 files, `with_vulkan` 8 / 4, `registered_*` 17 lines; `CapturedDecode` 48 lines in
5 files (fuel-dispatch, fuel-model-llama, fuel-model-phi, fuel-tensor); `realize_f32_cuda` 50 lines in 13 files
(fuel-transformers too).

**(2) Cure and cost.**
- K3 (5): a cure that does not break: `Storage` accessors (`as_cpu()`, `as_cuda()`) hold the match once; the helpers become thin
  and move to the adapter crates that use them. The helpers are `pub`, so removing them from `fuel-dispatch` is a **breaking
  change to a published crate** (`fuel-dispatch` 0.46.2 is on crates.io). Cost: about 5 files plus 3 adapter crates, one breaking
  minor.
- K2 (9): a handle trait in `fuel-backend-contract` (a `DeviceHandle` that the registry stores as `Arc<dyn ...>`) replaces
  `with_cuda(CudaDevice)` and friends. Breaking for the feature-gated `fuel-dispatch` API (callers: 3 crates, about 20 lines), so
  one breaking minor.
- K4 (6): `as_device` and `realize_f32_*` are `fuel-tensor`'s bridge to backend types; the cure is to move the backend-gated
  modules (`cuda_backend`, `metal_backend`, `vulkan_backend`) behind the seam row 137 step 6 names. Breaking for the few
  external callers (one example and the backend crates' doc comments use `vulkan_backend::as_device`).

These three are one programme (row 137 step 6), not three fixes, and they interact with GAP-380 (b) (the executor path) and the
Baracuda 0.46.0 launcher change; doing them before (b) risks churn in the files (b) edits (`fuel-dispatch/src/pipelined.rs`,
`dispatch.rs`).

**(3) Order.** After G1 (loaders). K3 first among these (smallest, mechanical), then K2, then K4; all after GAP-380 (b).

## 4. What I would accept for now, and why

Accepted findings are `allowlist` entries on `<component>:<item>` with an owner, a reason and a checkpoint, never configuration
that removes the path from the analyser.
- **K1 (4 sites).** Accepted by the 2026-11-01 ruling above; revisit trigger: "backends live outside Fuel" (then trait objects).
- **K2/K3/K4 (20 sites).** Accept until GAP-380 (b) lands, because (b) edits the same files and a refactor first would be
  rewritten; revisit checkpoint: ROADMAP row 137 step 6 start. Allowlist, not declaration change.
- **Not accepted:** G1/G2 (178). They have a cheap, non-breaking cure (step 1) and I would do it first. If the PM prefers to
  take the declaration view for `loaders` (policy, like `fuel-formats`) that is a defensible reading of the dependency graph; the
  measured effect is 204 to 24, but it leaves 135 files naming a file-mapping handle, and I would record that trade-off in the
  declaration comment rather than hide it.

## 5. What the splits look like once these edges are clean

Seam candidates are those of `2026-11-01-seams-and-cleanup-program.md`; row 139 needs its own go.
- **Seam 1 (format and interchange).** After steps 1-2, `fuel-formats` + `fuel-loaders` (+ `fuel-onnx`, tensor-tools) have no
  upward edge: the models name `fuel-formats` only. That is a project that depends on `fuel-ir` and `fuel-quantized`, which are
  the data model; so the split is real only if `fuel-quantized` and `fuel-ir` are consumed by version (they are crates.io
  deps already). Cheapest split to define, and it is where step 1 lands, which is why step 1 comes first.
- **Seam 3 (executor and backends).** Steps 3-5 are the cleanup row 137 prescribes for it; once K2-K4 are behind the contract the
  backends see `fuel-backend-contract` only and the closed enum stays in `fuel-memory`. The backends stay in the workspace (the
  ruling) so there is a seam crate (`fuel-backend-contract`), not a split, until backends go outside.
- **Not split:** IR, graph, optimizer, dispatch, storage: one data model (the design note's own exclusion).
- The ARC-004 count is the **ratchet** for seam 1 and seam 3: it goes 204 -> 24 after steps 1-2, -> 4 after steps 3-5, and the
  last 4 are the K1 ruling; a re-measure at each step is the exit test, with the positive control that the same command finds a
  known site (for example `DeviceRegistry::with_cuda`) before it.
