# Qwen3.5/3.8 27B (`qwen35`) on Fuel: loader, paged hybrid decode, Pascal route

Plan for the programme the PM adopted on 2026-11-14 (`[TASK] fuel-qwen35-plan`): #660 sharded GGUF (done, 0.47.31), then this
note, then ROADMAP row 118 (the `qwen35` quantized loader), then paged hybrid decode, then GAP-380 (b) when a GPU window

## 1. Evidence: what the real 27B file contains

**Source.** Hub repo `unsloth/Qwen3.8-27B-GGUF`, file `Qwen3.8-27B-UD-Q4_K_M.gguf`, 16,564,259,744 bytes (15.43 GiB; the hub
tree listing reports `size` = `lfs.size`; the repo has no split Q4_K_M, so it is one file). **Read** by two HTTP range
requests on `https://huggingface.co/unsloth/Qwen3.8-27B-GGUF/resolve/main/Qwen3.8-27B-UD-Q4_K_M.gguf`: bytes 0-8,388,607
(too short: the tokenizer arrays end later) and **bytes 0-33,554,431** (parsed in full). Nothing else was downloaded; no
file is on disk outside the scratchpad, and none is in a worktree. The metadata plus all tensor infos end at **byte
10,996,621**, so the first 10.5 MiB is the whole header; tensor data starts after that (alignment key absent, default 32).

GGUF v3, **866 tensors, 50 metadata keys**, `general.architecture = qwen35`, `general.file_type = 15` (Q4_K_M),
`general.quantized_by = Unsloth` (a "UD" dynamic mix, see the type table).

**Tensors (read).**
- Global: `token_embd.weight [5120, 248320]` (Q4_K), **`output.weight [5120, 248320]` (Q6_K), present**, so the 27B head is
  not tied (the 4B file had no `output.weight`), `output_norm.weight [5120]`.
- Recurrent block (e.g. `blk.0`): `attn_norm`, `post_attention_norm` `[5120]`; `attn_qkv.weight [5120, 10240]`,

  10240 = 6144 + 2 x (16 x 128): q, k (16 heads x 128) and v (48 heads x 128) concatenated, as in the 4B file.
- Full-attention block (e.g. `blk.3`): `attn_q.weight [5120, 12288]` (24 x 256 x 2: gated query), `attn_k/attn_v [5120, 1024]`,

- Layers with `attn_q.weight`: 3, 7, ..., 63 (**16**) **and 64**. So blocks 0-63 are 48 recurrent + 16 full attention
  (every fourth), and **block 64 is a full-attention block carrying `nextn.eh_proj [10240, 5120]`, `nextn.enorm`,
  `nextn.hnorm`, `nextn.shared_head_norm`**: the multi-token-prediction (speculative) head, which `nextn_predict_layers = 1`

- GGML types in the file (counts of tensors): F32 x360, Q8_0 (8) x107, Q3_K (11) x2, Q4_K (12) x74, Q5_K (13) x142,

  only 74 tensors. `ffn_down` is IQ4_XS in block 0, IQ4_NL in block 3 and Q6_K in block 64, so the type varies by tensor, not by kind.

**Corrections to what the repo already says.** `fuel-loaders/src/quantized/qwen35_names.rs` and row 118 say the output head
is tied and that the loader needs Q6_K/Q8_0 first. For this file: head untied; the loader must also take **IQ4_XS (142
tensors, the largest quantized class), Q5_K (142), Q4_K, IQ4_NL, IQ3_S, Q3_K**. `fuel-quantized` has IQ-family block types
(`fuel-quantized/src/cpu.rs`), which is **not** a check that every needed matmul path exists for each (see section 5).

**Still unproven.** This is a header read. The name map stays an **unverified hypothesis**: names and shapes match the 4B
file and the 4B scheme, but no tensor value of the 27B has been compared to Hugging Face. The two value rules in
`qwen35_names.rs` (norm gain may already include `+1`; `ssm_a` may be `-exp(A_log)`) and the q/k/v split and gate-half
order are still open, and a real 27B run is what closes them (milestone M2). A 27B file is not in `C:\models`; it is only
pulled when a run needs it (15.43 GiB; this box has an 8 GB GPU, so the first full run is CPU or the P40).

## 2. Sizes (arithmetic from section 1)

- Weights: 16,564,259,744 B = 15.43 GiB resident for the quantized model (host mmap or device).
- Per-sequence recurrent state, f32, per recurrent layer: S = 48 value heads x 128 x 128 = 786,432 floats = 3,145,728 B; conv
  history = (4 - 1) x 10,240 = 30,720 floats = 122,880 B. Per layer 3,268,608 B; x 48 layers = **156,893,184 B (149.6 MiB)
  per live sequence, constant in context length**.
- KV per token, f16: 4 kv heads x 256 x 2 (k and v) x 2 B = 4,096 B per full-attention layer; x 16 layers = **65,536 B per
  token** (the MTP block is not counted). 8,192 tokens = 512 MiB; the 262,144 context = 16 GiB.
- A P40 (24 GB, sm_61): weights 15.4 GiB + state + KV for a few sequences fits; the 4070 (8 GB) cannot hold the weights.

## 3. Slot layout and the hybrid paged trait

Today (row 117, `fuel-inference`): `HybridDecodeModel` owns a per-sequence `Cache` and `FixedState` is host-side, not plan-once,
and not paged. `PagedDecodeModel` (supertrait of `DecodeModel`) serves attention through `DeviceKvPool` + `SessionHandle`
and plan-once decode. The 27B needs both at once.

**Slot layout (proposal).** One `RecurrentStatePool` per model, sibling of `DeviceKvPool`: `N` equal slots, one per live
sequence, allocated at admission and freed at finish, never grown. A slot is 48 layer records of
`[conv: 3 x 10240 f32 | S: 48 x 128 x 128 f32]`, each record padded to 256 B, so a layer's state is one `(offset, len)` in the
slot. Slot count = the same bound that sizes `DeviceKvPool` (admission control counts both pools; a request that cannot get
both is queued, not half-admitted).

**Trait (proposal).** `PagedHybridDecodeModel: HybridDecodeModel` with
`forward_paged_hybrid_step(token, kv: &mut DeviceKvPool, kv_session: SessionHandle, state: &mut RecurrentStatePool, slot: StateSlot) -> Result<Vec<f32>>`
and a plan-once sibling mirroring `forward_paged_step_persistent`. Attention layers take the existing block-table path
(`Op::PagedAttn`, the 16 layers); recurrent layers read the slot as graph inputs and write the next state to graph outputs.
**All-or-nothing is kept by double buffering**: the step writes the next state into the slot's spare half and flips a
generation bit only on success, costing 2 x 149.6 MiB per live sequence (arithmetic) rather than the host copy row 117 uses.
A failed step leaves the previous half current, which is the property `HybridDecodeModel::step` already promises.
Batched paged decode (B = K) is **not** in scope here: GAP-380's bounding experiment decides the batched attention path
first, and recurrent layers batch trivially per slot only after the single-sequence path is correct.

**Prefix sharing is OFF for hybrid sessions, by design, not by omission.** The recurrent state after `p` tokens depends on all
`p` tokens; it cannot be rebuilt from shared KV blocks, so sharing a prefix's KV blocks without the matching state would give
silently wrong results. Semantics: a hybrid session never calls `PrefixCache` lookups or block sharing and never forks
(rows 150/151 apply to pure-attention models); admitting a hybrid model with prefix reuse requested returns a typed error,
not a silent fallback. A later feature is a state snapshot at a block boundary (149.6 MiB each, arithmetic); it is deferred and
recorded in ROADMAP row 155, with a GAP id to be allocated by the registry owner.

## 4. Loader plan (row 118)

1. `qwen35` `from_gguf` over `MmapedContent` (sharded or single, `bytes_at`), config from `qwen35.*` (all keys in section 1
   exist; `nextn_predict_layers` is read and block 64 is **skipped by plain decode and recorded**, not silently dropped).
2. Weights stay quantized to `QMatMul` (row 124 pattern). Per-tensor mixed types in one file are the norm here.
3. Apply the name map **as a hypothesis** and prove the value rules on a real run: milestone M2 compares the first-token logits of
   the quantized path with a CPU reference over the same weights (llama.cpp-independent: Fuel's own composed forward on
   dequantized weights, which matches HF on Qwen3.5-0.8B per row 115). A value rule is promoted from `Unverified*` to
   `AsIs`/named only by that comparison.

## 5. Pascal (P40, sm_61) route

Facts (PM notice p40-sm61-facts, **quoted, not re-derived**): Baracuda treats sm_61 as compile-only (NVRTC 12.9.86); its
hand-written kernels have no sm_61 path; f16 goes via f32. Baracuda's 0.46.0 `lower_kernel` stage 2 passes one by-value
params struct (works on every sm, no `__grid_constant__`), but its sm_61 NVRTC compile is **unconfirmed** and an NVRTC 13.x
rejects sm_61 (PM notice, 2026-11-14).

Explicit route, in order of preference; each step is a milestone with its own exit test:
- **P0 (CPU reference).** The same 27B graph on CPU (row 118 loader, f32 compute over dequantized blocks). Slow, but it is the
  oracle for M2 and for every device run after it.
- **P1 (f32 compute on sm_61).** Quantized weights stay resident; each matmul dequantizes a tile to f32 and uses an f32 GEMM,
  no f16 anywhere on this arch. Needs: an sm_61 build of the dequant and GEMM kernels (Baracuda NVRTC compile-only is the
  gap) for the **eight** quantized types in section 1. If Baracuda cannot supply them, the fallback is Fuel-internal
  kernels (a decision for the PM, not assumed).
- **P2 (dp4a).** sm_61 has int8 dot-product; an integer path for Q4_K/Q5_K/Q8_0 is an optimisation after P1 is correct.
- **P40 smoke run (milestone M3):** load the 27B Q4_K_M on the P40, decode 1 greedy token, compare the top-5 logits with the P0
  oracle for the same prompt; then 32 tokens, compare token ids. **There is no P40 on this box** (RTX 4070 Laptop 8 GB plus an
  AMD iGPU, `CLAUDE.md`); M3 needs a window on the machine that has one, through `scripts/gpu-run.ps1`, and the PM
  is told before and after.
