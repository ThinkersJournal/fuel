# Where the Qwen3 prefill time goes, with weight residency ON and OFF (row 170 / row 172 attribution, 2026-11-23)

Lane: fuel. Every number below is MEASURED. Predicate: Qwen3-0.6B Q4_K_M GGUF, 21-token prompt, Vulkan, RTX 4070 Laptop
(adapter 1, 8 GB), release build, `gpu-run`, executor backlog feed OFF. Tree: branch `weight-residency` at `c268ec146`
(row 172, residency default ON) plus the phase timers on branch `prefill-attrib` (`7bef2d4fd`, a REFERENCE branch: it
carries a measurement-only env read, so it is not meant to merge as is). Instrument: `examples/qwen3_vulkan_profile.rs`
with `QWEN3_PROFILE_PREFILL=1 QWEN3_PREFILL_TWICE=1`, args `2 3`: one process = one cold warm-up call, then 2 runs, each
a prefill in a fresh context and a second prefill in the same context. "Cold" = the first prefill of a process;
"later first-prefill" = a fresh context on a device that already holds the model. N and spread are on every table
(median [min..max], ms). Phases are `fuel_dispatch::compiled::op_profile::PhaseTimer` host wall times; they NEST, so
the tables subtract children from parents and print the remainder as UNATTRIBUTED, never folded into a phase.

## Result in one paragraph

On this tree **nothing is unattributed**: of the cold prefill 3.2 s (median of 5 processes, residency ON), 1.55 s is the
one-time weight upload (`residency.upload`, 311 weights), 1.08 s is `bridge.build_optimized_graph` (66 ms when warm; its
inside is NOT broken down), 0.30 s is building the graph, 0.15 s is the executor, 0.09 s is DROPPING the per-call graph
(`d1.drop_graph`, 92 ms, present in every prefill), and the rest is under 3 ms plus 0.3 ms unattributed. A warm prefill
(0.59 s) is graph build 315 ms, optimize 66, executor 111, graph drop 93-95, other 2. With residency OFF the same weight
upload (1.8 to 2.1 s) is paid in `bridge.prepare` on EVERY prefill (2.4 to 2.8 s each). I found no row that names an
"unattributed 1.7 s"; the nearest candidates are the OFF `bridge.prepare` 1.83 s and the ON cold `residency.upload`
1.55 s, which are the same H2D cost on two paths, and both are attributed here.

## The 92 ms outside the three d1 phases

A second build added `d1.total`, `persistent.total` and `persistent.drop_decode_session`: `WALL - persistent.total` is
0.2 to 0.4 ms, `drop_decode_session` is 0.0, and the 91 ms sits inside `d1.total` but outside build, warm and realize.
A third build timed the explicit `drop(built)` at the end of `forward_with_kv_context` (the per-call graph and its 311
weight Consts and their slots): `d1.drop_graph` = 92.2 [90.5..158.6] ms cold (N=3) and 95.2 [87.6..99.2] warm (N=6), and
wall - build - realize - drop = 0.3 [0.2..0.3] cold, 0.4 [0.2..0.9] warm. So the remainder is graph teardown, ~16% of a
warm prefill; why dropping a 21-token graph takes 92 ms (a large Drop of nodes and storage slots, or a lock) was not
investigated.

## Controls and caveats

- Known-answer control: `ATTRIB_SLEEP_MS=100` inside `residency.seed`: that row goes from 0.2 to 100.5 [100.3..100.6]
  (warm, N=6) and 100.5 [100.2..100.8] (second prefill, N=9), +100.3 as inserted; the WALL moved +78 (warm) and +79
  (second prefill) because the wall's own spread is 40 ms (build_graph 300 to 315 in the control runs against 315 to 317
  in the base runs). So the row is exact; whole-wall deltas of less than ~40 ms are inside the noise.
- The cold numbers are from one process each and the spread is large (cold wall 3.0 to 3.5 s, OFF cold up to 4.1 s; the
  last attribution build's 3 cold runs were 3.7 to 5.8 s, the box being busier). Quote the cold wall as 3.0 to 4.2 s.
- `bridge.build_optimized_graph` cold (1.08 s) against warm (66 ms): a 1 s first-use cost INSIDE a named phase whose
  contents are not attributed (candidate: first-use pipeline or plan creation; not tested). It is the largest cold item
  that has no explanation here.
- Not measured: CUDA, a loaded GPU, another model, the AMD iGPU, residency on a post-merge main (the tree is the
  residency branch merged with `58debefec`).

## Row 173, first breakdown: `d1.build_graph` is the weight copies; `d1.drop_graph` is freeing them (measured in situ, same day)

Hypothesis first (a stand-alone microbenchmark, `rustc -O`, black-boxed): copying 1,193 MB as one 622 MB f32 table plus
310 vectors of 1.84 MB (the Qwen3-0.6B f32 embedding table and ~570 MB of quantized words) takes 237 ms (6 rounds,
236.5 to 251.3) and dropping the copies takes 70 ms (66.3 to 74.7). That matched the 315 ms and 92 ms, so the next
step was to measure it in the real process. Code: `fuel-graph`'s `Arc`-fed `Const` constructors do
`HostBuffer::F32(v.to_vec())` (and U32, F64, BF16, F16, 15 call sites); branch `prefill-attrib` (`cb30de83b`, REFERENCE,
measurement only) wraps them in `timed_const_copy`, which adds the wall time, bytes and calls to three process-wide
counters that `qwen3_vulkan_profile` prints around the profiled prefill. Same predicate as above (residency ON, 3
processes; each process has one cold prefill and two warm ones; the counters are per profiled call):

| | cold prefill (N=3) | warm prefill (N=6) |
|---|---|---|
| `Const` array copies | 315 calls, 1,508 MB | 315 calls, 1,508 MB |
| time in those copies | 327.5 [291.8..425.3] ms | **312.1 [302.9..370.9] ms** |
| `d1.build_graph` | 335.7 [299.8..434.5] ms | **314.8 [305.7..374.4] ms** |
| build_graph minus the copies | 8.2 ms | **2.8 [2.6..3.5] ms** |
| copies / build_graph | 97.6% | **99.1% [99.1..99.2]** |
| `d1.drop_graph` | 94.6 [89.2..148.3] ms | 93.6 [82.5..103.8] ms |

So **99% of `d1.build_graph` is the `to_vec` copy of 315 source arrays** (1.5 GB: the f32 embedding table, every
quantized weight's `u32` words, and the small per-call arrays), and everything else the build does costs 2.8 ms.
`d1.drop_graph` (93.6 ms) is consistent with freeing those 1.5 GB (the stand-alone free of 1.19 GB took 70 ms), but that
was NOT timed in situ: the claim is "matches a free of that size", not "measured to be the free".

What a decode step does not do: the decode session holds its own graph and rebinds, so it never rebuilds the `Const`s.

Consequence (NOT built, NOT proposed for the hot path until the PM says so): with residency ON the uploaded storage is
already on the device and seeded into the realize cache, so the host copy the graph build makes is never read on a
warm call; it is 312 + ~90 ms of a 590 ms prefill (68%) spent building and freeing a host copy nothing uses. Whether a
`Const` could share the source `Arc` instead of copying (the `HostBuffer` would have to hold an `Arc<[T]>`) is a
design question for row 173 (d), with its own before/after on this predicate.

Still not broken down: the cold `bridge.build_optimized_graph` 1.08 s (row 173 (c)). The 1,508 MB count is larger than
the 1.19 GB the residency registry keeps per model because the counters also see the small per-call consts and every
copy, not only the resident weights; the split was not measured.

## Row 173 (c): the cold `bridge.build_optimized_graph` 1.08 s is `compile_plan` (measured, same day)

Optimizer stage timers on `prefill-attrib` (`8c78440c0`, REFERENCE, measurement only), cold first prefill of 3 processes
(residency ON; same predicate), ms per process: `bridge.build_optimized_graph` 1160.7 / 1168.1 / 1039.4 =
`opt.ensure_installed` 21.9 / 23.6 / 21.3 + `opt.topology_current` 0.1-0.2 + `opt.judge_oracle` 0.1-0.2 +
`opt.optimize_graph` 1138.5 / 1144.1 / 1017.8, and inside `optimize_graph`: **`opt.compile_plan` 1083.5 / 1088.9 / 963.4**
(95%), `opt.run_lockstep` 49.1 / 49.3 / 49.0, `opt.dtype_fixups` 1.1 / 1.0 / 0.9, the rest (placement stamping, residency
copies, layout fixups) 4.8 / 5.9 / 4.5. The WARM call (the second prefill of process 1): `build_optimized_graph` 65.2 =
`run_lockstep` 49.4 + `compile_plan` **10.5** + `dtype_fixups` 0.9 + ~4. So the cold cost is the placement DP / cost
composer / Judge lookup in `compile_plan` doing 1.0 s of FIRST-USE work that costs 10 ms once warm (a cache of some kind:
cost expressions, contract compilation, Judge cells, plan store; WHICH one was not timed). `run_lockstep` is a steady
49 ms on every call, a second small lever. `ensure_installed` (22 ms) and the topology and Judge accessors are not it.

Not done: what inside `compile_plan` warms (one more level of timers, or a flame graph); whether the first-use work can
be done at load time or persisted (row 162 is the plan cache).

## Row 173 (b) and (c) closed to a function (measured, same day; timers on `prefill-attrib` `c815e328f`, REFERENCE)

**(b) `d1.drop_graph` IS the free of the weight copies.** A global allocator wrapper (`fuel_graph::TimedAlloc`, installed
by the example) times every `dealloc` of a block of at least 1 MiB; around the explicit `drop(built)` it counts **142
calls, 1,471 MB, 86.8 [79.5..107.1] ms**, against `d1.drop_graph` 92.8 [85.0..112.8] ms: **93.4% [92.4..94.9]** of the
drop is those frees (N=18 paired calls over 3 processes, cold and warm alike, residency ON). The other ~6 ms are the
small frees and the node and slot drops. Row 173 can say "is".

**(c) The cold `compile_plan` 1.0 s is `SystemTopology::transfer_calibration()`, i.e. `TransferCalibration::calibrate`.**
Chain, each level timed: `opt.compile_plan` 995.8 / 1082.8 / 970.0 ms (cold, N=3) -> `cp.open_dp_row` (592 entries)
985.6 / 1072.5 / 960.4 -> `cp.dp.push_row` 1030.0 / 951.5 / 981.7 (second build) -> `topology.transfer_calibration_probe`
1029.6 / 951.0 / 981.3 (the `OnceLock` initialiser in `fuel-dispatch/src/topology.rs`, first reached from the DP's
`estimate_transfer_ns`); the other plan stages are `cp.build_node_draft` 3.2 ms (1557 entries) and
`cp.finalize_node_greedy` 0.2 ms; WARM `compile_plan` is 11.3 ms with `open_dp_row` 0.7 ms. Inside the probe
(`fuel-hardware/src/transfer_cost.rs`, `calibrate` -> `probe_vulkan_device` for BOTH Vulkan adapters on this box, gpu 0 and
gpu 1), ms per process for the pair of devices, N=3: **a second `VulkanBackend::with_selection` per adapter 205.8 / 256.9 /
269.9, the timed H2D and D2H round trips (`measure_calibration_points`, 64 KiB, 4 MiB, 64 MiB x 3) 607.8 / 700.7 / 558.4,
and `drop(backend)` 187.1 / 208.9 / 217.2**; they sum to the probe timer to within 0.2 ms (999.7 / 1166.5 / 1045.5 against 999.8 /
1166.7 / 1045.5). So the cold 1 s is: build and destroy a second Vulkan device per adapter (about 0.4 s) and time real
transfers (about 0.6 s), to price transfers for the placement DP, once per topology generation. **The calibration runs
TWICE per process in this example** (the startup "planner estimate" lines and the profiled prefill: the first probe of
the first process took 3.9 s, the cold driver and device creation, the later ones 0.65 to 1.2 s), because the topology
snapshot is rebuilt in between (cause not traced).

Controls: a known delay inside `topology.transfer_calibration_probe` (`ATTRIB_SLEEP2_MS`): +1000 ms shows as +1044 ms in
that row (2067.0 / 2049.7 / 1976.7 against 1029.6 / 951.0 / 981.3 / 1072.1, median 1005.5; the base spread is about
+-60 ms); a +100 ms sleep was run (N=3) and is NOT resolved against that spread (1001 / 1030 / 1009), so the 1000 ms control
is the one that counts. The `drop` counters are exact counts and times of the allocator calls, not an estimate.

Consequence (NOT built): the calibration result is machine state that changes rarely; row 162 (persistence) could
cache it across processes, and the second in-process probe is a plain waste. No hot-path change was made.
