Written 2026-11-03 at `origin/main` 043de464 (0.37.18). The PM's instruction: a read-and-plan note first,
the PR split by backend, each PR with its hand CUDA compile. Nothing in this note is built or run; every
number is a count over the committed tree and says which tool counted it.

## 1. How big the problem is (the "266 cfg lines" figure understated it)

ROADMAP row 137 gave "266 `cfg(feature = "cuda" | "vulkan" | "metal")` lines in 25 files". A fresh count over
`fuel-dispatch/src` and `tests` finds 280 lines naming `cuda`, `vulkan`, `metal` or `jit` in 50 files (218
cuda, 63 vulkan, 0 metal, 14 jit). Those lines guard 119 `fn`, 38 `use`, 27 match arms, 21 `mod`, 12 `struct`
and 10 `impl` (same count, by the item that follows the attribute). **A cfg-line count is the wrong measure**,
because whole modules hide behind one line. Counted in lines of code instead:

| what | lines | gated by |

| `vulkan_dispatch.rs` (Vulkan kernel bindings) | 8,503 | one inner `#![cfg(feature = "vulkan")]` |

| `jit_ingest.rs` 4,313 + `jit_ingest_probe.rs` 965 + `jit_adopt.rs` 539 + `jit_cuda_load.rs` 463 + `jit_carrier.rs` 299 + `kiss_corpus.rs` 682 | 7,261 | `feature = "jit"` (and `cuda`) |

## 2. What couples it (this is the finding that shapes the plan)

`fuel-cuda-backend` depends on `fuel-backend-contract`, `fuel-cpu-backend`, `fuel-graph`, `fuel-ir` and
`fuel-quantized`, not on `fuel-dispatch`; `fuel-dispatch` depends on it. So code that imports `crate::...` from
dispatch cannot simply move down into a backend crate.

A first look at the module graph is discouraging: the transitive closure of `baracuda_dispatch` and of
`vulkan_dispatch` is 22 modules and about 107,000 lines, nearly the whole crate, and `fkc` (33,464 lines) names
them 476 and 272 times while they name `fkc` back 70 and 30 times. **But the cycle is thin.** References *to* the backend
modules come from backend-gated modules almost entirely: `baracuda_dispatch` is named 466 times from
`fkc/cuda_link.rs`, 14 from `jit_ingest.rs`, 5 from `seed_cuda_accuracy.rs` and once each from five other cuda
modules; `vulkan_dispatch` 269 times from `fkc/vulkan_link.rs` and once each from three vulkan modules. Only
three references come from code that is not itself backend-gated:

- `dispatch.rs:8172` and `:8186`, in `register_optional_backends`: `register_baracuda_cuda_kernels(table)` and
  `register_vulkan_kernels(table)`;
- `pipelined.rs:7807`: `vulkan_dispatch::contiguize_vulkan(...)` in the executor's Vulkan arm.

What the backend modules need *from* the core is small: `kernel.rs` (2,129 lines, `BindingEntry` and the
binding table), `fused.rs` (2,265), the `fkc` descriptor types, `cost.rs` (1,148). That is the same surface
`fuel-aocl-cpu-backend` and `fuel-mkl-cpu-backend` already use: both sit **above** `fuel-dispatch`, import
`fuel_dispatch::kernel`, and are registered by an explicit call in `fuel-tensor/src/cpu_accel.rs`; a ratchet
(`fuel-ir/tests/registrar_callers.rs`) fails when a registrar has no caller.

Outside use of the modules that would move (code only, every workspace crate outside `fuel-dispatch`):
`fuel_dispatch::baracuda_dispatch` once (`fuel-tensor`), `vulkan_dispatch`, `fkc` and `jit_*` not at all,
`kernel` 23 times (`fuel-aocl-cpu-backend` 8, `fuel-mkl-cpu-backend` 9, `fuel-tensor` 6), `fused` once. crates.io
lists 8 reverse dependencies of `fuel-dispatch`, all Fuel workspace crates. So the Breaking blast radius is small.

## 3. Two designs, and the recommendation

**A. Backend-dispatch crates above dispatch (the aocl/mkl pattern).** New `fuel-cuda-dispatch` and
`fuel-vulkan-dispatch` (or a module inside each backend crate if its dependency set allows, which it does not:
the backend crates would then depend on `fuel-dispatch`, which depends on them). Each holds the kernel bindings,
the `fkc` link module, the verification seeds and (CUDA) the JIT; each exports one registrar. `fuel-dispatch`
loses the code and the two registration calls; `fuel-tensor` calls the registrars the way `cpu_accel.rs` does.

**B. Push the vocabulary down.** Move `kernel.rs`, `fused.rs` and the `fkc` descriptor types into a crate below
the backends and move the backend code into the backend crates. Larger: `kernel` and `fused` call each other and
`fkc` (18 and 3 references), and `fkc` is 33k lines whose core and backend halves are mixed.

**Recommendation: A**, because it reuses a pattern that exists and is ratcheted, moves the code with the fewest
edges cut, and leaves `kernel`/`fused`/`fkc` where they are. B stays available later.

**The one hazard A introduces.** `register_optional_backends` runs when the process-wide binding table is first
built, and readers take a snapshot of that table. A backend that registers *after* the first snapshot is missed
unless it uses the runtime extension path (`extend_global_bindings`). Today the CUDA and Vulkan kernels are
present from the first snapshot because dispatch registers them itself. Moving the call out must keep that
guarantee (registrars called before first use, or registered through the extension path with the same
visibility), and the oracle in section 4 exists to catch exactly this.

## 4. The PR sequence (each its own PR, behaviour-preserving, red-first where it changes anything)

**Oracle for every PR:** a census of the binding table before and after, built with the same features: for each
backend, the sorted list of `(op, dtype, layout class, source tag)` keys and the entry count, diffed. The move
passes only when the diff is empty. A sabotage sibling: drop one registration and confirm the census diff goes
red. Plus the backend's live tests.

1. **6.1 Vulkan first.** `vulkan_dispatch.rs` (8,503), `fkc/vulkan_link.rs` (960), the vulkan verify modules
   (about 1,100) and `contiguize_vulkan` (called once from `pipelined.rs`, which needs a small seam: the
   executor's Vulkan arm calls the function through the new crate). Vulkan first because it compiles in minutes
   and its live tests run under `gpu-run` with no CUDA forge. The census runs with `--features vulkan`.
2. **6.2 CUDA kernel bindings.** `baracuda_dispatch.rs` (7,258), `fkc/cuda_link.rs` (1,581), the cuda verify
   modules (about 3,500), `register_cuda_kernels` inside `dispatch.rs`, the `cuda` arms in `compiled.rs`.
   **Hand CUDA compile required** (no runner, board item 366), through a `cuda-build.ps1` slot with
   `fuel-dispatch/cuda` and `fuel-tensor/cuda` named together, plus `gpu-run` live tests. A cold forge is 56 to
   93 minutes, so one hand compile per PR, and a warm target directory matters.
3. **6.3 JIT.** `jit_*` and `kiss_corpus` (7,261), after 6.2 because `jit_ingest.rs` names `baracuda_dispatch`
   14 times and `kernel`/`fused` 49. CUDA-gated, so hand CUDA compile again.
4. **6.4 What is left:** the small `cuda`/`vulkan` cfgs in `dev_tools.rs`, `telemetry/judge_sink.rs`,
   `topology.rs`, `fkc/mod.rs`, `ledger.rs`, `runtime_fused_kernels.rs`, `lib.rs` (about 50 lines), and a
   re-count to close the row: "no cuda/vulkan/jit `mod` left in `fuel-dispatch/src` and every `match` arm over a
   backend enum variant is in `pipelined.rs` or `device_registry.rs` by design".

Version: each PR that removes a public path from `fuel-dispatch` is Breaking (`fuel_dispatch::baracuda_dispatch`
and `vulkan_dispatch` are `pub mod`), so a minor bump each under the pre-1.0 rule, unless `fuel-dispatch`
re-exports the moved module for a release; the outside use is one line in `fuel-tensor`, so I would not keep a
shim. The PM allocates the numbers.

## 5. Decisions needed before 6.1

1. **A or B** (above). Recommendation A.
2. **Crate names and count:** two crates (`fuel-cuda-dispatch`, `fuel-vulkan-dispatch`) versus one per backend
   inside an existing crate. A new workspace crate needs CI, branch-protection and publish handling and a
   version that matches the rest (one version per project).
3. **Registration:** explicit registrars called from `fuel-tensor` (the aocl/mkl pattern) versus dispatch
   keeping a feature-gated `register_optional_backends` that calls into the new crates. The second creates a
   dependency from dispatch to the new crates and defeats the move.
4. **Does the row-139 split plan change this?** Row 139's splits are held for CodeRipper 0.21.0, and
   `pipelined.rs` (16.5k lines) and `dispatch.rs` (13.3k) are the files it would split. This plan leaves both
   in place, so the two are independent, but a split of `dispatch.rs` would change where `register_cuda_kernels`
   lives.

## 6. What this note did not measure

- The coupling *inside* `baracuda_dispatch.rs` and `vulkan_dispatch.rs` (they name `dispatch` twice and once;
  whether either reaches a private item of `dispatch.rs` through a `pub(crate)` path was not checked).
- Whether `fuel-cuda-backend` or `fuel-vulkan-backend` already hold code that duplicates what would move.
- The `tests/` directory beyond counting cfg lines (about 25 files, one cfg line each, `baracuda_*_live.rs`).
- The cost of the CUDA hand compile per PR on a cold target directory; 56 to 93 minutes is the figure in
  CLAUDE.md for the forge, not a measurement of these PRs.
- Metal: no `metal` cfg exists in `fuel-dispatch`; nothing to move.
